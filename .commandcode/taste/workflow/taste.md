# workflow
- Verify all claims/reported statuses against actual repo disk state before executing; treat any artifact referenced only in conversation or reported-but-not-on-disk as non-existent ("if it's not on disk, it's not real") and commit planning docs to docs/. Confidence: 0.75
- When investigating a "that looks like a bug" flag, cross-validate with MULTIPLE independent checks (e.g. raw source pull, fresh random sample, relevant-code semantics, independent-signal agreement) before overturning/confirming the suspicion — a single re-check can only reproduce the original suspicion, not rule it out; a verified "not a bug" is a stronger result than an unconfirmed bug. Confidence: 0.80
- When a suspicious distribution/result is sampled from a larger pool, re-sample FRESH from the full pool (not re-slice the original sample) to rule out the original sample being unrepresentative — and scale the fresh sample up to match the original sample size before treating the finding as confirmed. Confidence: 0.80
- Keep verification gates strict: when a gate trips incidentally (e.g. a keyword in a docstring/comment), remove the incidental dependency rather than loosening or adding exceptions to the gate itself. Confidence: 0.65
- Build features strictly at their designated roadmap ticket in sequence (e.g. tournament.py at RM-006, submit.sh at RM-027); do not scaffold ahead of a ticket just because a downstream doc references it. Confidence: 0.70
- When a ticket/checklist assumption is stale or wrong (e.g. "import must exist" but adding it would be dead code), do NOT force a change to make the item literally true — flag the incorrect assumption, explain why, and move on. Confidence: 0.80
- Keep tunable constants in a single source of truth (config.py); do not duplicate tables like MARKET_PARAMS in other files (e.g. micro_tests.py) — dedupe by importing from config to avoid silent drift. Confidence: 0.75
- Convert silent failure modes into automated hard gates (e.g. a precheck script that replicates the engine loader) rather than docstring/documentation reminders — a docstring only protects you if you remember to read it before every edit, and the engine can quietly run the wrong function without erroring. Confidence: 0.80
- Treat a "skip X in v1" decision as a scope decision (deferred to a specific later ticket), not a strategic conclusion against X — X succeeding badly without the supporting logic doesn't prove X itself is bad (e.g. v1 losing money on land expansion ≠ land expansion is bad, only that it needs RM-014 task assignment first). Confidence: 0.65
- When a test's printed output disagrees with its shell exit code, double-check the verification method: a pipe stage (e.g. `cmd | head`) reports the LAST command's exit, so a passing pipe can mask a failing command upstream — verify raw (un-piped) exit codes separately before trusting a result. Confidence: 0.70
- Validate capability additions with a rigorous A/B tournament: compare CI lower bounds (land-buying-enabled vs. disabled, same opponent/seeds, >=80 paired games) and only promote a feature that measurably beats the baseline — don't ship "it still wins so it's fine"; a null result is valid and should be logged as deferred pending a specific reason, not silently shipped either way. Confidence: 0.80
- Assertions about a refactor's generality/payoff (e.g. "per-unit structure means hands reuse it with no code change") must be verified empirically, not assumed from code shape — the acceptance test is that the feature actually works end-to-end in the new pathway. Confidence: 0.70
- When a feature is deferred to a specific later ticket (e.g. land expansion parked at RM-016 pending hired hands), that later ticket's acceptance criteria must explicitly RE-RUN the deferred comparison with the unlocking capability in the loop (e.g. re-run the land A/B with hands enabled), so the decision is actually resolved rather than re-parked at yet another ticket. Confidence: 0.70
- Treat single-match replay/ladder observations as labeled soft priors, never as a distribution — they must not override a rigorous A/B tournament result (multi-game, fixed seeds, CI). Use replays only to sanity-check direction or to reconcile (not contradict) an A/B verdict by clarifying the conditions under which the skipped feature pays off. Confidence: 0.70
- Isolate one variable per A/B test: split multiple questions (e.g. two different crops, or a crop addition plus a land/hands re-toggle) into separate A/B runs rather than one combined test, so each result can be attributed to which variable actually moved the outcome — don't average/combine into a single "diversified" number. Confidence: 0.75
- Before re-running a twice-rejected A/B, require a concrete changed-input hypothesis (e.g. "does a higher-value crop mix make land/hands worth it?") rather than another A/B for its own sake — a stark repeated 0/160 rejection means the next test needs a real reason to believe the input mix changed. Confidence: 0.70
- When a fixed benchmark opponent becomes saturated (every variant returns an identical CI like 160/0), it can only confirm "not broken," never "better" — switch the promotion signal to self-play A/B (candidate vs. current-committed baseline) and demote the saturated opponent to regression-only smoke, so a real improvement shows up as a shifted win rate rather than an indistinguishable pin. Confidence: 0.75
- Build multi-stage pipeline features (e.g. buy→build→place→feed→harvest) incrementally and dormant-safe: verify each mechanical stage in isolation (a forced scenario proving the action sequence works), explicitly enumerate what the ticket does NOT do, and accept transiently-unprofitable intermediates (e.g. a starving animal before feeding exists) as expected proof-of-mechanic rather than a bug — keep the feature off by default and defer the "is it worth it" A/B to the ticket where the full cost can actually be measured. Confidence: 0.70
- When the user asks to work "one small ticket at a time," honor a strict approval-granularity pace: before executing, pause and present the relevant file contents (e.g. main.py/config.py) for review, then wait for the user's exact commands + small changes for that single ticket — do not jump ahead or implement the whole roadmap, and hold until the review completes before touching the next ticket. Confidence: 0.80
- Before any strategy/optimization work, freeze a reproducible baseline first (git tag at the current commit, fixed-seed performance stats, fresh smoke-test pass recorded in a README) so every future change has a measuring stick to beat — do not optimize while the baseline is still unmeasured. Confidence: 0.70
- When a feature's A/B proves it beat the current committed baseline (e.g. CI lower bound clears 0.50 with a decisive win rate), do not leave it deferred under an `*_ENABLED=False` default flag — promote it to the committed default immediately, before starting downstream work, so the next ticket builds on the correct (tested-better) baseline rather than a known-inferior one. Leaving a proven-promotable result dormant is itself a bug (a "built but not activated" state), not a neutral deferral. Confidence: 0.80
- Re-derive numeric constants/thresholds against the actual committed-baseline state rather than trusting inherited assumptions — a number in docs/strategy.md can be built on a false premise (e.g. assuming prior land already owned when the baseline owns nothing), and the fix is to recompute from the real current state, not to trust the inherited figure. Confidence: 0.70
- When a hard gate passes but the feature under test was never actually exercised, the pass is vacuous and must not be trusted — e.g. an animal-escape gate returning 0 escapes because the animal was never bought/placed, or a "stable" money figure that is actually a degenerate loop. Confirm the feature genuinely activated (buy/place happened, expected behavior ran) before trusting a green gate. Confidence: 0.80
- When a consumed resource has a production latency (e.g. wheat must be planted→matured before it can feed), a sell-side reserve buffer alone is insufficient — enforce a production-side floor (minimum planted tiles) and escalate the whole plant→water→harvest chain above competing tasks when the reserve is low, including making room (DIG a premium crop) when the field is full. Confidence: 0.80
- When an old A/B conclusion is found to rest on a non-functional parameter (a cosmetic flag/argument that never changed behavior, so the experiment never tested what it claimed), formally mark the old result RETRACTED (not merely superseded-by-new-data) across all docs with the reason, and audit sibling tickets that used the same mechanism for the same bug class rather than assuming them clean because the new ticket didn't name them. Confidence: 0.80
- Every "one sample/seat equal to a constant" symptom that turns out to be real behavior should also be checked for the opposite failure mode: a unit-state bug that silently disables the feature (e.g. a pickup/drop ping-pong, a second unit purchase that idles a worker) can masquerade as a working pipeline — trace the actual per-unit action sequence around the symptom before concluding root cause. Confidence: 0.70
- When analyzing large raw datasets (e.g. a multi-GB parquet of replays), do NOT parse the raw file — first look for pre-extracted/pre-parsed small tables (CSVs of per-episode features/outcomes) and analyze those directly, only opening a raw record one row at a time when a specific question needs the raw action streams. Confidence: 0.75
- When read_file/read_directory return "outside workspace (allowed: ...)", do not abort — inspect the file via shell_command instead (e.g. `cat`, `ls -la`, `head -1`, or a `python3 -` heredoc against CSV/parquet files) to read the content without moving it into the workspace. Confidence: 0.75
- A raw winner-vs-loser group-mean comparison has a skill confound: winners are better bots partly because they're better, so any feature that correlates with "being good" (e.g. more wheat planted) shows up spuriously — before promoting a correlational finding from leaderboard data, control for skill (compare within rating bands, or include `rating` as a control variable in the regression), not just raw group means. Confidence: 0.75
- When self-play win rate saturates (every variant returns an identical decisive score like 80/0, so ranking is impossible), switch the discriminator to an actual outcome margin (e.g. final-bank difference via a dev-only margin profiler) to find a cost ceiling — win rate can only confirm "not broken," while margin reveals where a cost (e.g. a hire fee) first exceeds marginal production. Confidence: 0.70
- In a ceiling/crossover search, commit the LAST Monotonic improvement, not the best single data point: if 3>2, 4>3 (decisive), but 5 vs 4 is negative and 6 vs 5 is positive (non-monotonic), commit at 4 — a non-monotonic recovery (6 beating 5 after 5 lost to 4) is a single-seed anomaly, not a reliable signal, so the defensible ceiling is the last step where every increment was a measurable win. Confidence: 0.70
- Even a skill-controlled regression can still yield a spurious causal signal via survivor/direction-of-causality bias: a positive coefficient may read "success → (late-game scaling of) X" as "X → success" when X only pays off after an economy is already established (e.g. strawberry's +$144 coefficient flipped to 0–4/80 in self-play because high-skill bots scale strawberry only after building wealth). Treat correlational leaderboard output as hypothesis-generation ONLY; self-play A/B against the committed baseline is the authoritative truth gate for causal direction, and when the two disagree, self-play wins. Confidence: 0.80
- Parallelizing an extract job only pays off if the bottleneck is CPU-bound — when the decode is I/O-bound on a single large file (e.g. one parquet), worker processes finish sequentially at the same interval regardless of worker count, so parallelizing buys nothing and the real fix is to sample/stratify rather than parallelize. When chunks complete sequentially despite parallelism, abandon the full pass and take an ample contiguous sample instead of burning time. Confidence: 0.70
- When merging CSVs/DataFrames, pandas 3.0 infers all-string `StringDtype` for some columns and silently produces a 0-row result on a join key type mismatch (string vs int) with no error — cast the join keys explicitly on read (`dtype={...}`) and sanity-check the merge returned >0 rows before trusting downstream output. Confidence: 0.70
- When merging CSVs via `cat`/`grep` in shell: `cat` silently concatenates per-file header rows (stray mid-file headers), and `grep` across multiple files prefixes each match with the filename — use `grep -hv` to suppress filenames and explicitly emit a single header, then verify no stray headers remain. Confidence: 0.70
- When self-play win rate saturates AND an external reference target exists (e.g. the leaderboard's ~$92k winner bank), switch the discriminator to ABSOLUTE outcome vs that external target, not just self-play margin — absolute final bank exposes a real scale gap (e.g. 3x here) that a pinned self-play record (80/0, 240/0) cannot. Measure both the candidate and the external target in the same units before concluding "improved." Confidence: 0.70
- A leaderboard bot's aggregate stats (peak_crew 14, tiles_planted 174) are downstream symptoms of an already-scaling farm, not actionable levers — naively copying them as config targets (hands=14, buy_land=True) reproduces the symptom WITHOUT the mechanism and crashes income (14 hands → $9.4k vs $31.5k baseline). Identify the underlying mechanism (per-tile production efficiency / assignment) before copying the number. Confidence: 0.70
- Before launching a long data-extraction pass (e.g. a full parquet decode), time a small sample to estimate end-to-end throughput first — if the estimate exceeds a few minutes, prefer parallelizing the independent records across cores (ProcessPoolExecutor over row-group chunks) or a rating-stratified sample over a single-threaded multi-hour run. When a parallel job shows no visible output, verify the workers are actually healthy (high CPU% with accumulating CPU-time, e.g. via `ps -eo etime,time,pcpu`) before concluding a hang — a 0-byte temp output can just be Python's write buffer waiting for a chunk to finish. Confidence: 0.70
- For a large/structural/risky change (vs a single knob), design first in plan mode with a data-grounded phased plan rather than jumping straight to code: ground the design in prior conversation context + dataset evidence, mark any unverified evidence gap explicitly (e.g. a Step 0 controlled regression to close before building), and split into independently testable neutral-safe phases so a failure remains attributable. Confidence: 0.70
- Pre-commit an explicit kill-criterion inside a data-driven design (e.g. "Step 0: if this predictor does not survive rating control, STOP and re-plan") and honor it when it fires — do NOT proceed to build a structural rework whose evidence gate already failed, even when the sunk context (plan written, user said "go ahead") pushes toward continuing. A design that builds in its own falsification check and actually stops on it is worth more than forging ahead on a disproven hypothesis. Confidence: 0.70
